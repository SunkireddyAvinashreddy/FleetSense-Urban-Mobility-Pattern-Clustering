# FleetSense — Urban Mobility Pattern Clustering

Unsupervised discovery of recurring urban mobility and footfall patterns from city-bus GPS
and on-board camera feeds, served as an animated live map and a model diagnostics console.

**Running now:** <http://127.0.0.1:8000/>

---

## 1. What it does

| Stage | Output |
|---|---|
| Ingest | 162k stop events, 314k camera rows, 329k GPS pings → 314,160-row stop × date × hour panel |
| Engineer | **31 behaviour features** per stop (demand bands, AM/PM concentration, dwell, speed consistency, capacity use, delay, entropy, crowd pressure, network degree…) |
| Cluster | **KMeans (k=8)** on scaled + PCA-reduced features → 8 mobility archetypes |
| Validate | Ward agglomeration, silhouette, Davies–Bouldin, Calinski–Harabasz, Adjusted Rand index |
| Detect | **DBSCAN** (density outliers) + **Isolation Forest** (stop and stop-hour anomalies) |
| Rhythm | Second KMeans on 24-dim normalised demand curves |
| Serve | FastAPI + React dashboard: live animated map, fleet control, route explorer, scenario lab |

### Results (current run)

| Metric | Value |
|---|---|
| Stops / buses / routes | **374 / 520 / 24** |
| Panel rows | **314,160** (35 days) |
| Features | **31** |
| Clusters (k) | **8** (silhouette-selected, parsimony rule) |
| Silhouette | **0.556** |
| ARI: KMeans vs Ward | **0.959** |
| Davies–Bouldin | **0.658** |
| PCA 2-D variance | **43.5 %** |
| Cluster label purity (post-hoc only) | **92.7 %** |

Recovered archetypes: Commuter Interchange Hub · Residential Outbound Feeder · Evening & Night
Footfall · Campus & College Zone · Market & Retail Footfall · Event & Leisure Venue ·
Shift-Work & Industrial · Airport & Gateway Transit · Low-Activity Peripheral.

No labels are used to fit any model. The generator's latent archetype is only read *after*
clustering to sanity-check the result.

## 3. Data

`pipeline/generate_data.py` simulates a fleet of **520 buses on 24 routes across 374
Bengaluru stops** for 35 days:

- `gps_pings.csv` — 1-minute positions, speed, heading, occupancy, delay
- `stop_events.csv` — every bus call: boardings, alightings, occupancy, dwell, approach speed, schedule deviation
- `camera_footfall.csv` — hourly pedestrian / two-wheeler / stopped-vehicle counts, crowd density, confidence
- `stops.csv`, `routes.csv`, `route_stops.csv`, `fleet.csv`, `daily_context.csv`

Demand is driven by 10 latent stop archetypes (including an airport gateway and an event venue)
with distinct 24-hour profiles, weekend multipliers, weather effects and AM/PM directionality,
then sampled with Poisson noise. Raw CSVs are git-ignored and regenerated by the pipeline.

### Engineered features (31)

`log_footfall`, `morning/midday/afternoon/evening/night_share`, `am_peak_ratio`, `pm_peak_ratio`,
`peak_to_base`, `temporal_entropy`, `night_activity`, `service_frequency`, `weekend_ratio`,
`daily_volatility`, `morning_balance`, `dwell_mean_s`, `dwell_per_boarding`, `speed_mean_kmh`,
`speed_consistency`, `occupancy_mean`, `capacity_utilization`, `schedule_delay_mean_s`,
`delay_index`, `routes_served`, `footfall_per_route`, `ped_to_rider_ratio`, `two_wheeler_share`,
`crowd_density`, `crowd_pressure`, `neighbour_demand_ratio`, `network_degree`.

## 4. Models and why

| Model | Role | Rationale |
|---|---|---|
| StandardScaler + PCA(8) | pre-processing | removes unit bias, decorrelates the 31 features |
| KMeans on 6 PCs | primary clustering | compact, fast enough to score new stops in real time |
| Ward agglomeration | validation | ARI 0.96 confirms the partition is not an artefact of initialisation |
| DBSCAN (3 PCs) | outlier discovery | density-based, no need to pre-specify how many anomalies exist |
| Isolation Forest | anomaly scoring | multivariate rarity on 374 stops and 314k stop-hours |
| KMeans (24-dim curves) | rhythm layer | captures *when* demand happens separately from *how much* |

k is selected from k = 3…12 by silhouette, then the smallest k within 3 % of the best score
is chosen so the model does not over-fragment for a marginal gain.

## 5. Dashboard

| Page | What it shows |
|---|---|
| **Overview** | KPIs, demand trend, archetype donut, hourly demand, busiest corridors, top stops, model scorecard |
| **Live Map** | Animated buses (340 markers) moving on route polylines, camera events, cluster overlay, per-bus card with speed / occupancy / next stop |
| **Routes** | All 24 corridors: geometry map, hourly curve, punctuality matrix, live vehicles, composition |
| **Clusters** | Archetype cards, 24-h curves, hour × archetype heatmap, cluster fingerprint, stop table |
| **Fleet Live** | Streaming vehicle table, load distribution, camera detections, replay state |
| **Anomalies** | PCA latent-space scatter, stop outliers, anomalous stop-hours, detector explanations |
| **Model** | Algorithm stack, k-selection, explained variance, feature matrix, centroid heatmap, purity, rhythms |
| **Scenario Lab** | 12 sliders → live `POST /api/predict`, confidence bars, expected curve, nearest real stops |

Live telemetry is a recorded GPS replay advanced at **14× realtime** with server-side
interpolation between pings, so buses glide continuously rather than jumping between samples.

## 6. Run it

```bash
pip install -r requirements.txt
python pipeline/run_pipeline.py     # first time only: generate + train (~3 min)
python run.py                       # http://127.0.0.1:8000
```

Frontend development (hot reload, proxies `/api` to :8000):

```bash
cd frontend && npm install && npm run dev     # http://localhost:5173
```

`start.sh` / `start.bat` build-if-missing and launch in one step.

### Known limitations

- The dataset is synthetic (calibrated to plausible fleet volumes), not a real city feed.
- Live mode replays recorded GPS rather than connecting to a production AVL stream.
- Archetype names are heuristic labels derived from centroids, not ground truth.
- KMeans assumes roughly spherical clusters; HDBSCAN on stop-hour vectors is the natural next step.
- Anomaly thresholds use fixed contamination rates; production would tune these per zone.
